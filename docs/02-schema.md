# 02 — Database schema

PostgreSQL 16. Conventions: `uuid` primary keys generated by `gen_random_uuid()`; `timestamptz` everywhere; `created_at`/`updated_at` on mutable rows; snake_case; every FK indexed; enums as Postgres enums (Drizzle `pgEnum`). All tables live in the `public` schema. Drizzle definitions go in `apps/api/src/db/schema.ts`; migrations are generated by drizzle-kit and committed as SQL.

## Enums

```sql
CREATE TYPE progress_status  AS ENUM ('not_started','in_progress','completed');
CREATE TYPE exercise_kind    AS ENUM ('perceptron','mlp','tokenizer','embeddings','attention',
                                      'prompt','structured_output','agent','harness');
CREATE TYPE question_kind    AS ENUM ('single_choice','multi_choice','numeric','short_text');
CREATE TYPE run_kind         AS ENUM ('prompt','structured','agent','harness');
CREATE TYPE run_status       AS ENUM ('running','completed','failed','cancelled','max_iterations');
CREATE TYPE step_kind        AS ENUM ('model_call','tool_call','tool_result','final','error');
CREATE TYPE auth_event_type  AS ENUM ('register','login_success','login_failed','lockout',
                                      'mfa_challenge','mfa_success','mfa_failed',
                                      'mfa_enrolled','mfa_disabled','backup_code_used','backup_codes_regenerated',
                                      'password_changed','logout','session_revoked');
```

## Identity & auth

### users
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| email | citext UNIQUE NOT NULL | `citext` extension for case-insensitive uniqueness |
| password_hash | text NOT NULL | argon2id encoded string (includes params + salt) |
| display_name | text NOT NULL | |

| locked_until | timestamptz NULL | soft lockout after 10 failures (15 min) |
| created_at, updated_at | timestamptz | |

### mfa_totp  (one row per user; row exists during enrollment before confirmation)
| column | type | notes |
|---|---|---|
| user_id | uuid PK FK→users ON DELETE CASCADE | 1:1 |
| secret_ciphertext | bytea NOT NULL | AES-256-GCM of the base32 secret |
| secret_iv | bytea NOT NULL | 12 bytes |
| secret_tag | bytea NOT NULL | 16-byte GCM auth tag |
| key_version | smallint NOT NULL DEFAULT 1 | allows key rotation later |
| confirmed_at | timestamptz NULL | NULL = enrollment pending; pending rows older than 1 h are deleted |
| last_used_step | bigint NULL | TOTP counter of the last accepted code; reject `step <= last_used_step` (replay protection) |
| created_at | timestamptz | |

### mfa_backup_codes
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK→users CASCADE | index |
| code_hash | text NOT NULL | argon2id (codes are 10 chars base32 → ~50 bits, hashing still cheap at 10 rows) |
| used_at | timestamptz NULL | single use |
| created_at | timestamptz | |

### sessions
| column | type | notes |
|---|---|---|
| id | bytea PK | `sha256(token)`; the raw 32-byte token lives only in the cookie |
| user_id | uuid FK→users CASCADE | index |
| mfa_verified_at | timestamptz NULL | NULL on a *pending* session for an MFA-enabled user; guards require non-null when `users.mfa_enabled` |
| created_at | timestamptz NOT NULL | absolute lifetime measured from here (30 d) |
| last_seen_at | timestamptz NOT NULL | idle timeout measured from here (7 d); updated at most once per 5 min |
| expires_at | timestamptz NOT NULL | pending sessions: created_at + 10 min; full sessions: min(idle, absolute) — recomputed on touch |
| ip | inet NULL | |
| user_agent | text NULL | |
| revoked_at | timestamptz NULL | logout / revoke-all / password change |
Index on `(user_id, revoked_at)` and on `expires_at` for the cleanup job.

### auth_events  (append-only audit log)
| column | type | notes |
|---|---|---|
| id | bigserial PK | |
| user_id | uuid NULL FK→users SET NULL | NULL for failed logins against unknown emails |
| event_type | auth_event_type NOT NULL | |
| ip | inet NULL | |
| user_agent | text NULL | |
| metadata | jsonb NOT NULL DEFAULT '{}' | e.g. `{reason:'bad_password'}`; never store secrets or codes |

### exercises  (one primary exercise per module, but the schema allows more)
| column | type | notes |
|---|---|---|
| id | uuid PK (v5) | |
| module_id | uuid FK→modules CASCADE | |
| lesson_id | uuid NULL FK→lessons SET NULL | optional anchor "appears after lesson X" |
| slug | text NOT NULL | UNIQUE (module_id, slug) |
| title | text NOT NULL | |
| kind | exercise_kind NOT NULL | selects the React component |

**Why jsonb here:** exercise configuration is authored, hierarchical, and never queried by its inner fields. Normalising "datasets" and "tasks" into tables would add joins for zero benefit.

### View: `v_user_module_progress`
Computed, not stored, until it is measurably slow (it won't be for one user):
```sql
SELECT u.id AS user_id, m.id AS module_id,
       count(l.id)                                        AS lessons_total,
       count(ulp.lesson_id) FILTER (WHERE ulp.status='completed') AS lessons_done,
       bool_or(uep.status='completed')                    AS exercise_done,
       bool_or(qa.passed)                                 AS quiz_passed,
       (count(l.id)=count(ulp.lesson_id) FILTER (WHERE ulp.status='completed')
        AND bool_or(uep.status='completed') AND bool_or(qa.passed)) AS module_completed
FROM users u CROSS JOIN modules m
LEFT JOIN lessons l                ON l.module_id=m.id
LEFT JOIN user_lesson_progress ulp ON ulp.lesson_id=l.id AND ulp.user_id=u.id
LEFT JOIN exercises e              ON e.module_id=m.id
LEFT JOIN user_exercise_progress uep ON uep.exercise_id=e.id AND uep.user_id=u.id
LEFT JOIN quizzes q                ON q.module_id=m.id
LEFT JOIN quiz_attempts qa         ON qa.quiz_id=q.id AND qa.user_id=u.id
GROUP BY u.id, m.id;
```
(Roadmap milestone: measure it with `EXPLAIN ANALYZE`, then decide whether to materialise. That is a real DB-design lesson.)

## Normalisation notes (what was decided and why)
- **Normalised:** users/sessions/MFA (security data must be exact and revocable), progress tables keyed by (user, item), attempts and answers (needed for history and per-question analytics), runs and steps (needed for SLI queries like "p95 model latency" and "parse-failure rate per tool").
- **Denormalised on purpose:** `users.mfa_enabled` (read on every request), `quiz_attempts.passed` (historical truth), rollup counters on `agent_runs` (cheap SLI queries), `exercises.config`/`quiz_questions.options` as jsonb (authored content, never filtered on).
- **Deferred:** materialised progress; per-user content versions; soft-delete on users (hard delete with cascade is fine for a solo app, and exercising `ON DELETE CASCADE` is instructive).
